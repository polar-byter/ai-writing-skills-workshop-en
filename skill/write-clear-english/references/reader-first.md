# Reader, purpose and continuity

Use this reference with [SKILL.md](../SKILL.md) for articles and substantial explanatory edits.

## Match the promise to the material

Identify what the reader can understand, decide or do after reading. Then separate that outcome from the exercise or software used to reach it. A short function can teach how a tool result reaches a model without qualifying someone to build a production agent platform.

Check broad phrases in headings. "Organize the work" needs an object and a recognizable outcome: whose work, what operations and what can be checked? Preserve the author's intended relationship instead of deleting half the purpose to produce a shorter title. A subsection can rely on context already established; it does not need to restate the entire course promise.

## Make the benefit imaginable

Connect the material to a task, decision or project the reader can picture. An analyst may need to investigate why an answer contradicts a policy. A manager may need to see where approval is required and what record remains after a change. These are possible applications, not evidence that every reader suddenly wants to study system internals.

Account for existing experience. Someone may already upload documents to a chat application. Explain what the exercise adds: inspecting the data path, changing a rule, connecting an operation or evaluating a product more precisely. Do not pretend existing tools cannot do useful work merely to justify a lesson.

Strong professional language needs corresponding actions. Requirements, integration design and acceptance criteria become meaningful when the reader can specify sources, permitted actions, missing-data conditions and checks. A list of career promises cannot substitute for those actions.

## Check the reasoning before the rhythm

Recover the author's claim before editing it. Distinguish a fact, inference, opinion and proposal. Ask whether the source supports the particular conclusion and whether a local example has been strengthened into a universal statement. Narrow or qualify unsupported claims; do not replace them with a familiar slogan.

Read neighboring sentences as a development of one thought. Explain how a new statement follows: an example, a reason, a consequence or a comparison. Words such as "therefore" do not supply a missing premise. Smooth wording cannot repair an invented causal relationship.

Prefer concrete observations over unexplained mechanisms. If a recruiter found suitable applicants among rejected resumes, say what matched the criteria and what remains to investigate. Do not add an unexplained "uncertain answer" or an imagined model confidence score.

## Keep the reader oriented

Introduce the current setting before discussing a request or instruction. Is the person typing in a chat application, editing a project file or calling a Python function? The reader needs that setting to interpret phrases such as "in this task" or "the model receives the rules".

When a new section follows a pause, briefly restore the program's purpose, the user's request, the participating components and the data passed between them. A previous lesson or a link is not a substitute for the minimal reminder needed to understand the next operation.

Before changing an example, announce the change and its purpose. A query can change from `python` to `py` to demonstrate substring matching, but the transition must explain that it is a separate experiment. Return to the main query afterward. Do not force one example to serve every topic if a different example would explain the point better.

## Name actions instead of vague locations

"The lines remained in Python" leaves the important distinction unexplained. If search returned a list but the next model request did not include it, say so. The relevant event is a missing transfer, not a mysterious place where the data stayed.

The same applies to shorthand such as "the function sees the notes" or "change the connection outside". Identify the argument, selected callable or return value. Ask which operation the shorthand hides before replacing a single word. Metaphor and professional language can be useful when they do not require the beginner to reconstruct the mechanism.

Keep observation separate from explanation. Seeing an unsupported answer does not prove that the instruction failed to arrive, and one successful answer does not establish that a skill always forces compliance. Check the visible input and state the remaining uncertainty.

## Write connected sentences

Combine parts of the same thought with simple relationships. "The model requested a search for python using find_notes" describes one operation more clearly than wording that makes the function call and the search sound independent. Distinguish what the model can request from what the program can execute.

Use sentence length to serve the explanation. A series of fragments can be harder to follow than one clear sentence, while a chain of qualifications can hide the main action. Pause when the subject or reasoning changes, not after each small fact.

Technical labels should not replace missing nouns when their role matters. "Pass the command to the dispatch_tool function" can orient a newcomer; once the function is established, repeating the noun everywhere becomes unnecessary.

## Edit the passage as a whole

Check facts, logic, examples, transitions and phrasing in that order. Read the paragraph independently of what you intended it to mean. Preserve important conditions and the author's voice. Delete repetition or an unsupported detour deliberately, not as an easy way to avoid explaining a useful idea.

Finally inspect headings, notes, captions and the next section. A clear paragraph between confusing neighbors still leaves the reader with extra work.
